# BIRDS - Border Incident Reporting & Documentation System

**Headquarters Border Guard Bangladesh (BGB)**  
*Confidential Operational Command & Surveillance Portal*

This folder is the React frontend. It has no data of its own: every screen reads from and writes to the BIRDS REST API in `../server` (see `../server/README.md`), which enforces permissions, workflow rules and auditing.

---

## Demo Access & Credentials

The development database is seeded with one account per role:

| Role | Username | Password | Scope / Unit | Key Permissions |
| :--- | :--- | :--- | :--- | :--- |
| **HQ Administrator** | `hq_admin` | `Admin@123` | HQ | Full administration, closes incidents, audit trail |
| **Sector Officer** | `sector_off` | `Sector@123` | Sector-7 | Files and reviews incidents in Sector-7, analytics, reports |
| **Battalion Operator** | `batt_op` | `Batt@123` | 17 BGB | Files and edits incident reports for 17 BGB |
| **Verifier / Approver** | `verifier` | `Verify@123` | Sector-7 | Verifies and approves reviewed incidents |
| **Auditor** | `auditor` | `Audit@123` | HQ | Read-only records, reports and the audit trail |

The login page offers these as shortcuts under `npm run dev` only (or when `VITE_SHOW_DEMO_ACCOUNTS=true` is set for a TEC demonstration build).

## Core Features & Modules

### 1. Command Dashboard (`/`)
- KPI cards (total, open, pending review, approved/closed, high & critical), scoped to the user's unit.
- Category doughnut with subcategory drill-down; 12-month trend (incidents, high/critical, approved/closed).
- Sector activity with risk scores; the five most recent incidents.

### 2. 3-Step Incident Filing Wizard (`/incidents/new`, `/incidents/:id/edit`)
- Classification (category, subcategory, severity), date/time (no future dates), Sector → Battalion → BOP limited to the user's area, GPS from the device or entered manually.
- Evidence: JPEG, PNG, GIF, PDF, MP4, MOV up to 50 MB each. Files upload when the report is saved; the server checks file content, hashes it (SHA-256) and keeps EXIF/GPS metadata.
- Save as draft, submit, and resubmit after a return.

### 3. Incident Detail (`/incidents/:id`)
- Full record, map, timeline with reviewer notes, evidence download and integrity check.
- Workflow buttons come from the server for the signed-in user (role, status, area, separation of duties). Return and reject ask for a reason.

### 4. GIS Map (`/map`), Analytics (`/analytics`), Reports (`/reports`)
- Map markers grouped by location with the two most recent incidents.
- Analytics by day / week / month / quarter / year with a previous-year comparison, severity, sector risk and category breakdowns.
- Four report templates; Excel and CSV exports are generated by the server with the *CONFIDENTIAL // OPERATIONAL* banner; PDF via the browser print layout.

### 5. Audit Trail (`/audit`)
- Server-side search and paging over the append-only, SHA-256 hash-chained audit log; on-demand chain verification; CSV/Excel export.

### 6. Administration (`/admin`)
- Users (create, edit role/scope, deactivate, unlock, reset password with a one-time temporary password), role permission matrix, categories, organizational hierarchy, password/session/retention settings, system status.
- **Operations (DEMO)**: backups, disaster recovery, high availability, performance targets and log management, laid out as they will appear in production. Not functional in the demo version; buttons say so and illustrative values are marked SAMPLE.

### 7. Account
- Change password (`/change-password`); forced after an administrator reset or for a new account.
- Idle sign-out after the configured timeout; the server applies the same limit.

## Standards

- Dates are shown as `DD-MM-YYYY`; times are Bangladesh Standard Time.
- Official BGB crest (`/bgb.png`) on the login page, header and printable reports.
- FontAwesome icons only in the interface (zero emoji policy).
- Responsive from phone to command-centre screens.

## Technical Stack

React 19, Vite 8, React Router 7, TailwindCSS 4, Leaflet + React Leaflet, Chart.js + react-chartjs-2, FontAwesome 6.

Source layout: `src/api/` (one module per API resource; `client.js` handles tokens and refresh), `src/context/AppContext.jsx` (session, policy, reference data, notifications), `src/pages/`, `src/components/`.

## Local Development

1. Start the API first (from `../server`; see its README):
   ```bash
   npm run db:start
   npm run dev          # http://localhost:4000/api/v1
   ```
2. Start the frontend:
   ```bash
   cd BGB
   npm install
   npm run dev          # http://localhost:5173
   ```
   Vite forwards `/api` to `http://localhost:4000` (override with `BIRDS_API_TARGET`; see `.env.example`). The app calls `/api/v1` on its own origin so the refresh cookie stays first-party.

3. Production build: `npm run build` (output in `dist/`).

## Deployment

The built `dist/` is a static site, but it must be served **on the same origin as the API**: a reverse proxy (Nginx, CLAUDE.md §15) serves `dist/` and forwards `/api/` to the Node.js API. Sessions use an httpOnly `SameSite=Strict` cookie scoped to `/api/v1/auth`, which only works same-origin.

`vercel.json` (SPA rewrite only) deploys the frontend **without** an API, so sign-in shows "Cannot reach the BIRDS API". A hosted demo needs the API deployed and proxied too (see DOUBT-010 in `../doubt.md`).
